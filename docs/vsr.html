Viewstamped Replication Made Live

By Pekka Enberg — Sep 5th, 2026

Viewstamped Replication is the oldest of the three protocols that keep a replicated state machine consistent by electing a primary. Oki and Liskov published it in 1988, a year before Paxos was written up, and Liskov and Cowling revised it in 2012 into the form most people read today: Viewstamped Replication Revisited. The revision has one distinctive feature. It is specified to run with no disk at all. A replica that crashes and forgets everything asks the others what it missed.

I have spent the past while implementing the protocol, testing it in a deterministic simulator, and building a machine-checked proof of its safety. This post summarizes the paper that came out of that, Viewstamped Replication Made Live, whose title borrows from Google's Paxos Made Live for a reason that will become clear.

The paper is not the protocol

The 2012 paper argues its own correctness informally, and read literally, it is not safe. There are three places where an implementation that follows the text loses committed data or executes an operation twice:

  • Recovery forgets the view. The paper replaces the disk write of the 1988 protocol with a round of StartViewChange messages, on the argument that a replica cannot forget it took part in a view change if a majority saw it start one. But a replica can crash after sending StartViewChange and before anyone receives it, recover into the old view, and then receive the responses to a message it has no memory of sending. It completes a view change it never intended, while the old primary keeps committing. The fix is the one write the 1988 protocol made and the 2012 paper gave up: persist the view number.
  • State transfer truncates. A replica that learns of a later view is told to cut its log back to its commit number before asking for the new view's log. If it had acknowledged an entry past that point, the entry may have been committed on the strength of that acknowledgement, and the replica's later vote no longer carries it. The fix is to never truncate: keep the log, ask for the suffix after the commit number, and replace only that.
  • The commit number can go backwards. A StartView may legitimately carry a commit number lower than the receiver's. If the receiver adopts it, the next Prepare re-executes operations it already applied. The fix is that the commit number only moves forward, from any message.

None of this is new. The recovery defect was found by Michael, Ports, Sharma, and Szekeres; the truncation and commit-number defects by Jack Vanlightly's TLA+ analysis. What is new is that an implementation has to adopt all three fixes at once, and then runs a protocol that no single paper states. That was also the situation Chandra, Griesemer, and Redstone described in Paxos Made Live: the algorithm with a proof is not the one you can run, and the one you can run has no proof. This paper is an attempt to close that gap for Viewstamped Replication. It states the corrected protocol as pseudocode and proves it safe.

What is proved

The setting is a cluster of N ≥ 2 replicas on a network that can lose, delay, duplicate, and reorder messages, where replicas crash and come back with nothing but their persisted view number. Each replica r has a log Lr and a commit number kr, the length of the prefix it has committed. A quorum is Q = ⌊N/2⌋ + 1. Write R for the set of replicas that are not currently recovering. The two main results are these.

Theorem 1.1 (Log safety). In every reachable cluster state:

  1. Prefix agreement. If i < ka and i < kb then La[i] = Lb[i].
  2. Durability. For every r in R and i < kr, at least |R| + 1 − Q replicas in R hold Lr[i] at index i.
  3. Commit bounded. kr ≤ |Lr|.

Theorem 1.2 (Linearizability). Every history of client requests and replies of a reachable cluster is linearizable with respect to the sequential state machine.

Prefix agreement says two replicas that have both committed an index hold the same entry there. Durability says every quorum the non-recovering replicas could form contains a replica holding each committed entry, so no view change can lose one; with nobody recovering, that is a majority. A recovering replica holds nothing and votes for nothing, so it counts on neither side. Linearizability is what a client sees: replies are consistent with a single sequential execution that respects the order in which requests were issued.

How it is proved

Neither theorem survives a single protocol step on its own. When a PrepareOk completes a quorum and the primary commits, whether the entry is now on a majority depends on what the other acknowledgements said, and nothing in the theorem statement records that. So the statement has to be strengthened until it closes on itself: an inductive invariant, a property that holds at startup and that no single step can make false. Once you have one, it holds forever, and the theorems are read off from it.

The invariant is stated over the history: the set of every message ever sent, from which delivery never removes anything. Replicas forget. A view change replaces a backup's log. But the PrepareOk that backup sent in the old view stays in the history, and the invariant quantifies over that. The history also makes the network model one rule: delivery picks any message ever sent, which covers loss, delay, duplication, and reordering at once.

The invariant has five named parts:

  • Local. Each replica's own fields are consistent: the commit number is within the log, the last normal view is not ahead of the current view.
  • Well-formed. Each message's fields agree with each other: a StartView's log is as long as it claims.
  • View-agreement. Within a view, an index determines its entry. Every piece of view v's log anywhere in the history, and every replica whose log came from v, agrees wherever they overlap. This is the property Raft calls log matching, with views for terms. It holds because a view has one primary and the primary is the only replica that appends in it.
  • Commits-backed. Every commit number, on a replica or in a message, is justified: each index below it was acknowledged by a quorum in some view.
  • Survival. Whatever was committed in a view is held, at the same index, by every later view's log.

Survival is where the paper's informal argument lives, made precise. The lemma that carries it says: if view v was started from a quorum of votes, and some entry was committed at index i in an earlier view u, then the vote from which v's log was chosen holds that entry at i. The proof is a strong induction on v. The quorum that acknowledged the entry and the quorum that voted intersect in some replica, and that replica either still holds the entry from view u, or adopted it from the log of a view between u and v, to which the hypothesis applies.

Each of the three corrections is what makes one step of that argument go through. Without the persisted view number, a replica's view can go backwards, and the induction has no order to run on. Without the ban on truncation, a vote need not cover what its sender acknowledged, and the intersecting replica may have lost the entry. Without monotone commits, Commits-backed fails at the replica that adopted a lower number. The paper makes this explicit: every correction is named against the clause of the invariant it keeps true.

Structure of the paper

The paper follows the shape of an algorithms paper rather than a systems paper. The main theorems are stated in the introduction. The preliminaries define the cluster, the history, and the invariant. A framework section then states the interface of every handler as a lemma, in the form precondition, effect, guarantee, and proves the theorems from those interfaces before showing a line of pseudocode. The protocol itself follows, one section per sub-protocol, each with the pseudocode, an overview, and the analysis that discharges its interface lemmas. The published protocol and its corrections are an appendix, for readers who want to see where the 2012 text leads wrong.

The proofs in the paper are sketches. The full proofs are being machine-checked in Lean 4 against a model that is one definition per function of the implementation, with the same control flow, and the model's correspondence to the code is tested by replaying the same traces on both. That part is still in progress, and the paper says so.

The paper draft, the implementation, the simulator, and the Lean model are at github.com/penberg/vsr-rs.
